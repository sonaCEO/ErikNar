# Telegram-темы и архив заявок ErikNar

## Цель

Сотрудницы работают с активными заявками в отдельных темах Telegram, находят их
по короткому номеру и не видят старые заявки в рабочем списке. Завершённые и
отклонённые заявки остаются активными 24 часа, затем бот добавляет их в общий
архивный журнал и закрывает исходную тему без удаления переписки.

## Номер заявки

У заявки появляется неизменяемое целочисленное поле `number`. PostgreSQL выдаёт
его из sequence, поэтому параллельные запросы не создают одинаковые номера.
Номер уникален, индексируется и показывается как `№0007`. UUID сохраняется как
публичный технический идентификатор для API и идемпотентности.

Миграция назначает номера существующим заявкам в порядке `created_at, id`, затем
делает поле обязательным. API создания заявки и административные ответы начинают
возвращать `number`; старое поле `public_id` остаётся для обратной совместимости.

## Жизненный цикл темы

При создании заявки бот создаёт тему:

`🆕 №0007 · Новая · Модель B`

Карточка содержит короткий номер и кнопку «Взять в работу». После назначения бот
редактирует название темы:

`🟡 №0007 · В работе · Сона`

Карточка показывает ответственного и кнопки «Завершить» и «Отклонить».
Финальное действие меняет название темы на один из вариантов:

- `✅ №0007 · Завершена`;
- `❌ №0007 · Отклонена`.

Кнопки после финального действия удаляются. Повторные и недопустимые действия не
меняют данные и возвращают сотруднику конкретную причину.

Telegram не умеет переносить тему вместе с сообщениями в другую тему. Поэтому
исходная тема через 24 часа закрывается, но не удаляется: переписка остаётся
доступной через поиск по короткому номеру.

## Общая тема «Архив»

В рабочей супергруппе один раз создаётся тема «Архив». Её `message_thread_id`
хранится в переменной `ERIKNAR_TELEGRAM_ARCHIVE_TOPIC_ID`. Настройка выполняется
явно при подключении рабочей группы, чтобы повторный запуск приложения не создавал
дублирующие архивные темы.

Через 24 часа после `closed_at` бот публикует в «Архиве» компактную запись:

- номер заявки;
- итоговый статус;
- дата создания и закрытия;
- клиент и телефон;
- модель и комплектация;
- ответственный сотрудник;
- ссылка на исходную Telegram-тему, если Telegram позволяет сформировать её для
  текущего типа группы.

После успешной публикации исходная тема закрывается. Архивная запись не содержит
полный UUID, но UUID остаётся доступным администраторам через API.

## Надёжность архивирования

При переводе заявки в финальный статус в той же транзакции создаётся событие
`lead.archive_due` с `next_attempt_at = closed_at + 24 часа`. Существующая
транзакционная outbox-очередь обрабатывает событие только после этого времени.

Обработка состоит из двух внешних действий: отправки архивной записи и закрытия
исходной темы. В заявке сохраняются `telegram_archive_message_id` и
`telegram_archived_at`. Если Telegram подтвердил действие, но PostgreSQL временно
не записал результат, событие получает `requires_review=true` и не повторяет
внешнее действие вслепую. Временные сетевые ошибки используют существующие
повторные попытки с ограниченной задержкой.

Одна заявка может иметь только одно активное событие `lead.archive_due`. Повторное
нажатие кнопки или повторный запуск воркера не создают вторую архивную запись.

## Компоненты

- миграция PostgreSQL добавляет номер и поля состояния архива;
- модели и JSON-схемы возвращают короткий номер;
- форматтеры формируют название темы, карточку и архивную запись;
- Telegram gateway получает операции переименования и закрытия темы, а также
  отправки сообщения в архивную тему;
- обработчик кнопок после успешной транзакции обновляет карточку и название темы;
- outbox processor обрабатывает как публикацию новой заявки, так и отложенное
  архивирование;
- Telegram worker остаётся единым процессом для polling и outbox, отдельный
  планировщик не требуется.

## Проверки

Автоматические тесты покрывают:

- уникальность и последовательность номеров при параллельном создании;
- миграцию существующих заявок;
- формат названий для каждого статуса;
- набор кнопок для каждого статуса;
- создание ровно одного архивного события;
- отсутствие обработки до истечения 24 часов;
- одну архивную публикацию при повторном запуске;
- повторные попытки при сетевой ошибке;
- закрытие темы только после архивной публикации;
- сохранение истории и запрет недопустимых переходов.

Ручной сквозной тест создаёт заявку, назначает сотрудника, завершает её с
ускоренной задержкой в тестовом окружении и проверяет архивную запись и закрытие
исходной темы.
